# Error investigation and repair

- Investigate and fix the underlying cause of errors completely. Do not suppress logs, hide error messages, disable checks, or bypass failing behavior merely to make an error disappear from view.
- Verify that the affected behavior works after the repair and retain useful diagnostics. If the cause or verification remains unresolved, report it explicitly rather than presenting hidden symptoms as a completed fix.

# Mandatory post-test diagnostics and fixed archives

- Before every automated, native, runtime or client-assisted test, record the existing crash files and relevant log lengths/timestamps. After every test, check for new or changed crash reports in the canonical `build-extractors/bin/Release/Crashes` directory and the test's own runtime directory. Inspect the test exit status, captured stdout/stderr, newly appended server warnings/errors/assertions, and newly appended `DBErrors.log` entries. A passing assertion or ready message is not sufficient if the process crashed or logged an unexplained failure.
- Investigate and repair every newly discovered error before calling the affected work complete. Keep unresolved evidence visible and explicitly marked unresolved; never empty a log or move an unexplained crash into `fixed` merely to make the active directories appear clean. An expected failing baseline must be identified as a counterfactual and paired with the passing repaired regression, not confused with a successful ordinary run.
- Once the specific cause is repaired, the repair is present in the tested/deployed binary or data, and the relevant regression passes, archive the resolved crash reports and diagnostic logs under the ignored local `build-extractors/bin/Release/fixed/` directory, grouped by issue/date. Preserve original bytes and verify archive hashes; record the cause, fix commit, checks and archive location in a non-sensitive audit. Never commit dumps, runtime logs, credentials or character data.
- After verifying the archive, remove only the resolved reports from the active `Crashes` directory and leave that active directory empty when no unresolved crashes remain. For a wholly reviewed/resolved `DBErrors.log` or other error log, retain its archived copy and truncate/recreate the active file to zero bytes so subsequent errors are clearly new. Do not clear mixed or partially reviewed logs; do not remove unrelated runtime files or informative server history indiscriminately.
- Never rotate or truncate a log being written by a user/unknown server. Ask before any maintenance requiring that server to stop; otherwise continue independent work and defer cleanup. Recheck for new files/appended bytes immediately before archiving so a concurrent new error cannot be discarded. Preserve Windows Defender quarantine and other security boundaries; fixed archives are not a way to bypass a blocked executable.
- Include the post-test diagnostic result and any unresolved errors or deferred archive/deployment in handoff. The presence of an empty active directory/log means only that its reviewed issues are resolved, not that every quest, visual or possible crash is verified.
