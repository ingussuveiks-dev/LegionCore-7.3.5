# The Scythe of Souls summon ownership

The 7.3.5 client showed overlapping Allari guides at Illidari Stand. The saved quest objectives recorded her arrival (90401) and still required the conversation (90403). The four crystal templates were already bound to the quest handler. Its release order begins with that conversation.

The quest starter's SmartAI casts the original 178711 summon with properties 3634. The recovery update used the overload of `WorldObject::SummonCreature` that passed null properties to the map. `TempSummon::InitStats` returns before adding those summons to the owner's list. The update could consequently summon Allari every second, and selecting an untracked copy could never satisfy the ownership check. The same overload also kept the personal demons out of the exit and retry cleanup paths. The existing fixture had modeled raw summons as tracked.

Recovery now uses properties 3634 for Allari and sets the original summon spell ID. Both the recovery attempt and any delayed original summon use the owner list to keep one guide. The recovery guide and soul actors are visible to their owner before map publication. The custom soul summons use properties 2912 to enter native owner tracking. The local 26972 DB2 contains both properties. The guide and all crystals still require the actual conversation, ordered releases, successful compel hits, combat victory, and return as applicable. No character progress or database rows were written.

Release compiled and linked against the original generated scripts, game, and shared libraries. The link map resolves the summon helper to `scripts:azsuna_scythe.obj`. The staged and canonical worldserver SHA-256 is `3BF87EA855B09B580AD4481965AD53FF9D1927FCD8A81FEDA683E4F51E48D3C6`. The matching map and previous rollback pair were verified by hash. Worldserver was absent immediately before deployment. The user-led gameplay workflow deferred execution of the updated fixture, other automated tests, and agent-owned startup. The natural conversation and crystal sequence remain pending in the client.

The user-owned previous process logged shutdown at 14:09:49. Its crash report at 14:09:52 resolves through its matching rollback map to `Trinity::Assert` in `Map::~Map`, called by `MapManager::UnloadAll`. This happened before the new executable was linked. The underlying shutdown invariant remains unresolved. The crash reports and old executable/map are retained for investigation. No subsequent crash or appended database error appeared during the build or deployment.
